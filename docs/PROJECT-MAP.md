# 코드 지도
## 저장소 구조 규약
- `front` (`public-front`) — React 19 + Vite + TypeScript 기반 SPA. `src/api/`에 백엔드 게이트웨이 REST·SSE 통신 모듈을 두고, `src/components/`(일반 화면 및 `ai/`, `admin/` 하위 도메인)에 UI 컴포넌트를 배치한다. 전역 인증 상태는 `src/context/`에서 관리하며, 실시간 채팅 WebSocket 연결은 `src/hooks/useChatSocket.ts`와 `src/flatbuffers/`(FlatBuffers 직렬화)가 담당한다.
- `python-server` (`public-python-server`) — FastAPI 기반 AI 마이크로서비스(`src/ai_service/`). 진입점 `main.py` 아래 도메인별 디렉토리(`rag/`, `knowledge/`, `llm_gateway/`, `prompt/`, `feedback/`, `observability/`)마다 `router.py`(HTTP 입구), `service.py` 또는 `application/*_use_case.py`(로직), `repository.py`(MongoDB·Qdrant·Redis 저장), `schemas.py`(도메인 모델 및 계약), `dependencies.py`(DI)를 둔다. Kafka 이벤트 소비자는 `infrastructure/messaging/*_consumer.py`에 모이며, 각 도메인 하위 `domain/*`, `presentation/`, `infrastructure/persistence/` 등의 빈 디렉토리는 계층 단순화 리팩터링 과정에서 남은 흔적이다.
- `server` (`public-server`) — NestJS 모노레포(`apps/*`, `libs/*`). 외부 HTTP·SSE·WebSocket 요청은 `apps/gateway`가 단독 진입점으로 받아 내부 마이크로서비스(`apps/identity`, `apps/payment`, `apps/chat-service`, `apps/admin-server`)에 gRPC(`*.grpc-controller.ts`)로 위임하거나, `apps/gateway/src/ai/proxy/*-proxy.controller.ts`를 통해 `public-python-server`로 HTTP 프록시한다. 공통 인증(`libs/auth`), gRPC·FlatBuffers 계약(`libs/rpc`), DB·로깅·예외 처리(`libs/common`)는 `libs/`에 모이며, `apps/ai-service`는 Python 서버로 이관되기 전의 레거시 NestJS AI 애플리케이션이다.

## 아쉬운 곳
- **지식베이스 실패 문서 재시도가 원본 파일 재처리 대신 단순 파일 선택창만 띄운다** — `public-python-server/src/ai_service/knowledge/router.py:26-53`, `public-server/apps/gateway/src/ai/proxy/knowledge-proxy.controller.ts:34-56` (`KnowledgeProxyController`), `public-python-server/src/ai_service/knowledge/application/ingest_document_use_case.py:93-107` (`IngestDocumentUseCase.execute`), `public-front/src/components/AiService.tsx:521-523, 976-978` (`handleRetryUpload`, `AiService`). 백엔드는 실패 시 재처리를 위해 원본 파일을 보존(`save_original_file`)하고 동일 `document_id`에 대한 재인제스트 분기를 지원하지만, 재인제스트 전용 엔드포인트(`POST /{document_id}/retry`)와 게이트웨이 프록시 라우트가 부재하다. 이로 인해 프론트엔드 문서 목록의 실패 행 [재시도] 버튼은 기존 문서를 재인제스트하지 않고 단순 파일 선택 다이얼로그(`fileInputRef.current?.click()`)만 띄워, 사용자가 파일을 다시 찾아 새로 업로드해야 하고 DB에 실패 문서가 중복 방치된다.
- **에이전틱 RAG 루프에서 생성된 정제 쿼리(`next_query`)가 검색에만 사용되고 이벤트나 세션에 남지 않아 추적이 불가능하다** — `public-python-server/src/ai_service/rag/application/agentic_ask_use_case.py:193-210` (`AgenticAskUseCase.execute`), `public-python-server/src/ai_service/rag/application/critique_generator_service.py:20-25, 81` (`CritiqueOutput`, `Critique.of`). 에이전틱 RAG 비평 단계에서 품질이 부족할 경우 다음 검색을 위해 `next_query`를 도출하여 루프 내 재검색(`query_refiner.refine`)에 사용하지만, SSE 이벤트(`_emit_progress`)나 최종 완료 메타데이터(`AskDoneMeta`), 세션 턴 기록(`TurnRecord`)에 반영되지 않고 버려진다. 사용자와 관리자는 AI가 어떤 재작성 쿼리로 추가 지식을 탐색했는지 파악할 수 없다.
- **LLM 비용 집계 시 모델별 합계만 남기고 상세 지표를 버리며 기간 조회 파라미터가 프론트에서 무시된다** — `public-python-server/src/ai_service/llm_gateway/repository.py:29-53` (`LlmCostLogRepository.persist`, `sum_by_model`), `public-front/src/api/aiAdmin.ts:70-73` (`getLlmCosts`), `public-front/src/components/admin/LlmMonitor.tsx:15, 36-50` (`loadData`, `LlmMonitor`). 비용 로그마다 `feature`, `promptTokens`, `completionTokens`, `fallbackUsed`, `attemptedModels`를 저장하지만 집계 시 `totalCostUsd` 외에는 모두 버린다. 또한 백엔드 API는 `from`/`to` 기간 조회를 지원하지만 프론트엔드가 파라미터 없이 호출하며 기간 선택 UI가 없어 관리자는 원하는 기간별 비용이나 상세 토큰 사용량을 확인할 수 없다.
- **질문 스트리밍 실패 시 원인별 세부 에러 메시지가 계산된 직후 하드코딩된 단일 문구로 덮어써져 뭉뚱그려진다** — `public-front/src/components/AiService.tsx:695-719` (`startQuestionStreaming` 내 에러 콜백). 스트림 수신 실패 시 `errorDetails` 변수를 선언하여 Error 객체 메시지, 가드레일 정책 차단 사유 등 상세한 원인 문자열을 추출하지만, 곧바로 상단 에러 배너에는 무조건 `setErrorMsg('답변 수신 도중 에러가 발생했습니다.')`로 하드코딩 덮어쓴다. 사용자는 네트워크 단절, 토큰 한도 초과, 가드레일 차단 등 실제 실패 원인을 파악하기 어렵다.
- **결제 시스템에 결제 취소·환불 도메인 로직 및 상태가 전무하여 되돌릴 수 없는 결제만 존재한다** — `public-server/apps/payment/src/payment/domain/model/payment-status.enum.ts:1-5` (`PaymentStatus`), `public-server/apps/payment/src/payment/application/create-payment.use-case.ts:27-94` (`CreatePaymentUseCase`), `public-front/src/components/PaymentHistory.tsx:16-95` (`PaymentHistory`). 결제 도메인 모델에 `CANCELLED` 또는 `REFUNDED` 상태가 아예 정의되어 있지 않으며 취소·환불 유스케이스가 부재하다. 결제 내역 화면에서도 결제 완료 건에 대한 취소 요청 UI가 없어 한번 승인된 결제는 시스템상 되돌릴 방법이 없다.
- **RAGAS 품질 평가 서비스(`RagasEvalService.evaluate`)가 백엔드 질문 처리 흐름에 연결되지 않았고 평가 결과 저장 시 답변과 컨텍스트를 버린다** — `public-python-server/src/ai_service/observability/service.py:71-90` (`RagasEvalService.evaluate`), `public-python-server/src/ai_service/rag/infrastructure/messaging/ask_requested_consumer.py:92-220` (`AskRequestedConsumer._process`), `public-python-server/src/ai_service/observability/schemas.py:16-23` (`RagasEvaluation`), `public-front/src/components/admin/RagasEvalPanel.tsx:130-165` (`RagasEvalPanel`). 품질 평가 서비스와 의존성 주입은 구현되어 있으나 RAG 컨슈머 및 질의 유스케이스 어디에서도 `RagasEvalService.evaluate`를 트리거하지 않는다. 또한 평가 수행 시 `payload.answer`와 `payload.contexts`를 받아 점수를 산출한 후 도메인 엔티티 저장 시 `question`과 지표 점수 3개만 남기고 답변 본문과 컨텍스트를 버려 관리자 모니터링 화면에서 불량 답변의 근거를 추적할 수 없다.
