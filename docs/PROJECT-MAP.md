# 코드 지도
## 저장소 구조 규약
- `front` (`public-front`) — React 19 + Vite + TypeScript 기반 SPA. `src/api/`에 백엔드 게이트웨이 REST·SSE 통신 모듈을 두고, `src/components/`(일반 화면 및 `ai/`, `admin/` 하위 도메인)에 UI 컴포넌트를 배치한다. 전역 인증 상태는 `src/context/`에서 관리하며, 실시간 채팅 WebSocket 연결은 `src/hooks/useChatSocket.ts`와 `src/flatbuffers/`(FlatBuffers 직렬화)가 담당한다.
- `python-server` (`public-python-server`) — FastAPI 기반 AI 마이크로서비스(`src/ai_service/`). 진입점 `main.py` 아래 도메인별 디렉토리(`rag/`, `knowledge/`, `llm_gateway/`, `prompt/`, `feedback/`, `observability/`)마다 `router.py`(HTTP 입구), `service.py` 또는 `application/*_use_case.py`(로직), `repository.py`(MongoDB·Qdrant·Redis 저장), `schemas.py`(도메인 모델 및 계약), `dependencies.py`(DI)를 둔다. Kafka 이벤트 소비자는 `infrastructure/messaging/*_consumer.py`에 모이며, 각 도메인 하위 `domain/*`, `presentation/`, `infrastructure/persistence/` 등의 빈 디렉토리는 계층 단순화 리팩터링 과정에서 남은 흔적이다.
- `server` (`public-server`) — NestJS 모노레포(`apps/*`, `libs/*`). 외부 HTTP·SSE·WebSocket 요청은 `apps/gateway`가 단독 진입점으로 받아 내부 마이크로서비스(`apps/identity`, `apps/payment`, `apps/chat-service`, `apps/admin-server`)에 gRPC(`*.grpc-controller.ts`)로 위임하거나, `apps/gateway/src/ai/proxy/*-proxy.controller.ts`를 통해 `public-python-server`로 HTTP 프록시한다. 공통 인증(`libs/auth`), gRPC·FlatBuffers 계약(`libs/rpc`), DB·로깅·예외 처리(`libs/common`)는 `libs/`에 모이며, `apps/ai-service`는 Python 서버로 이관되기 전의 레거시 NestJS AI 애플리케이션이다.

## 아쉬운 곳
- **보관함 답변 클릭 시 해당 턴 위치로 이동하지 않고 삭제 시 확인 안전장치가 없다** — `public-front/src/components/AiService.tsx:1388` (`AiService`), `public-front/src/components/AiService.tsx:336-345` (`handleDeleteBookmark`), `public-front/src/components/AiService.tsx:457-485` (`handleLoadSession`), `public-front/src/api/ai.ts:288-296` (`BookmarkItem`). 북마크 항목은 어떤 턴을 보관했는지 나타내는 `turnIndex` 필드를 갖고 있으나, 클릭 핸들러에서 `handleLoadSession(b.sessionId)`만 호출하여 턴 정보를 버린다. 이로 인해 긴 대화 세션에서 보관한 답변을 열면 첫 턴부터 노출되어 사용자가 수동으로 스크롤하며 찾아야 한다. 또한 보관함의 삭제 버튼(`✕`) 클릭 시 확인 팝업 없이 즉시 `deleteBookmark`를 호출해 영구 삭제하므로 실수에 의한 데이터 유실을 방지할 수 없으며, 답변 단위 보관과 세션 단위 보관 간의 시각적 구분(배지)도 없다.
- **근거 미참조·저신뢰도 답변의 피드백 연계가 단절되어 있고 불만족 사유가 재질문 시 누락된다** — `public-front/src/components/AiService.tsx:1581-1616` (`AiService`), `public-front/src/components/AiService.tsx:947-957` (`handleRefineFeedbackQuestion`), `public-front/src/components/AnswerFeedback.tsx:112-136` (`AnswerFeedback`). 지식베이스 문서를 찾지 못한 근거 미발견 답변(`isUngrounded`)에는 질문 구체화나 피드백 진입 버튼이 아예 없고, 저신뢰도 배너(`isLowConfidence`)에도 피드백 바로가기가 없어 메시지 버블 맨 아래까지 스크롤해야 한다. 또한 1~2점 불만족 피드백 제출 후 [질문 보완하여 다시 질문] 버튼 클릭 시 사용자가 선택한 불만족 사유 태그(예: [근거 문서와 다름], [환각/사실 오류])가 질문 입력창에 반영되지 않고 직전 원문 질문만 복원된다.
- **게임 유저 로그인·회원가입 토큰에 계정 ID(`id`)가 누락되어 모든 유저가 `accountId = 0`으로 결제 내역을 공유한다** — `public-server/apps/gateway/src/identity/identity-gateway.controller.ts:59-63, 81-85` (`IdentityGatewayController.login`, `register`), `public-server/apps/gateway/src/auth/gateway-auth.guard.ts:67-72` (`GatewayAuthGuard.canActivate`), `public-server/apps/gateway/src/payment/payment-gateway.controller.ts:51, 76` (`createPayment`, `listPayments`). 로그인/회원가입 응답 본문에는 `accountId: Number(reply.id)`를 반환하지만 정작 JWT 토큰 페이로드(`makeAuthToken`)에는 `id`를 넣지 않는다. 이로 인해 인증 가드가 세션 생성 시 `gameDbId: user.id ?? 0`으로 항상 `0`을 주입하여, 모든 게임 유저의 결제 생성 및 조회가 `accountId: 0`으로 위임되는 치명적인 계정 간 결제 데이터 오염이 발생한다.
- **결제 시스템에 결제 취소·환불 도메인 로직 및 상태가 전무하여 되돌릴 수 없는 결제만 존재한다** — `public-server/apps/payment/src/payment/domain/model/payment-status.enum.ts:1-5` (`PaymentStatus`), `public-server/apps/payment/src/payment/application/create-payment.use-case.ts:27-94` (`CreatePaymentUseCase`), `public-front/src/components/PaymentHistory.tsx:80-129` (`PaymentHistory`). `PaymentStatus` 열거형에 `PENDING`, `COMPLETED`, `FAILED`만 존재하고 `CANCELLED` 또는 `REFUNDED`가 정의되어 있지 않으며 취소·환불 유스케이스가 부재하다. 결제 내역 화면에서도 결제 완료 건에 대한 취소 요청 UI가 없어 한번 승인된 결제는 시스템상 되돌릴 방법이 없다.
- **지식베이스 문서 인제스트 실패 시 실패 원인 및 에러 상세가 버려져 사용자가 원인을 알 수 없다** — `public-python-server/src/ai_service/knowledge/application/ingest_document_use_case.py:128-132` (`IngestDocumentUseCase.execute`), `public-python-server/src/ai_service/knowledge/schemas.py:71-81` (`Document.mark_failed`, `DocumentProps`), `public-front/src/components/AiService.tsx:1120-1164` (`AiService`). 문서 인제스트 과정에서 RAG 콘텐츠 인젝션 탐지 차단, 파싱 실패, 임베딩 API 장애 등이 발생해도 예외를 로깅만 하고 `document.mark_failed()`로 상태만 `failed`, 청크 수를 0으로 저장한다. 스키마에 에러 원인 필드가 없어 프론트엔드 문서 관리 테이블에서도 단순 'failed' 뱃지만 노출되고 구체적인 실패 사유를 안내받지 못한다.
